# Crafty Accounting

Self-hosted bookkeeping for UK sole traders (cash basis), filing by Self Assessment return or through HMRC's Making Tax Digital (MTD) self-employment APIs. It started out for craft fair sellers (the sample data still is), but isn't limited to them. Keep README.md user-facing and short; implementation detail belongs here. README.md covers features, setup, Docker, HTTPS and backups; read it first.

**Status:** v1.0.0 is released but not yet in use with real books (as of 2026-10-28), so changes to the app and database structure are still fine. It stays a self-hosted web app; a native macOS version was considered and dropped.

## Layout

npm workspaces, all TypeScript:
- `shared/` (`@crafty/shared`): consumed as source, no build. Tax years, money, categories, zod schemas, API types, MTD and SA103S calculations (`mtd.ts`, `selfAssessment.ts`), mileage rates (`mileage.ts`), use of home flat rate (`useOfHome.ts`), Income Tax and Class 4 rates and the tax estimate (`taxEstimate.ts`).
- `server/`: Express 5 + better-sqlite3, bundled with tsup. Routes in `src/routes/`, SQL in `src/repo.ts`, migrations in `src/db/migrations.ts`, backup/restore/reset in `src/backup.ts`, daily backups in `src/autoBackup.ts`, people and password hashing in `src/users.ts`, the live-update event stream in `src/liveUpdates.ts`, the HMRC OAuth connection, token refresh and `callHmrc` in `src/hmrc.ts` (calls go through `ctx.fetch`, which tests replace), HMRC's fraud prevention headers in `src/fraudPrevention.ts`. Tests in `src/app.test.ts` (Vitest + supertest against a temporary database).
- `client/`: Vite, React 19, react-router 7, TanStack Query, react-hook-form, Tailwind v4, Recharts, lucide-react. API hooks in `src/lib/queries.ts`, theme tokens in `src/index.css`.

## Commands

Node 22 comes from Homebrew and isn't on the default PATH. Prefix shell commands with:

```bash
export PATH="/opt/homebrew/opt/node@22/bin:$PATH"
```

- If `node_modules` is missing (it can be cleared between sessions), run `npm ci` first.
- `npm run typecheck`: shared, server and client.
- `npx vitest run`: all tests. Run both before every commit.
- `npm run build`, `npm run seed`, `docker compose up -d --build`.
- `install-docker.sh`: the Docker Compose equivalent (source and `.env` in `~/crafty-accounting`; it refuses a folder holding an `install.sh` install, and that one refuses a Docker folder; `COMPOSE_PROJECT_NAME=crafty-accounting` pinned in `.env`, so it shares volumes with a checkout run by hand; `CRAFTY_PROJECT` overrides it for tests). Its body is in `main()` so an update can overwrite the running file; run from an install's folder it updates that install. Browsers send no server name (SNI) for an IP address and Docker's port mapping hides the address they used, so Caddy's `default_sni` is set to `SITE_IP` (the installer writes it, and adds it on update from the IP in `SITE_ADDRESS`); without it, browsing by IP fails the TLS handshake. The Caddyfile serves Caddy's root certificate at `/crafty-root.crt` (straight from its data folder, `XDG_DATA_HOME`), and both installers print its SHA-256 fingerprint and a Mac command that downloads it, checks the fingerprint and trusts it (`cert_help`; plus the PEM on a first install). Any address not in `SITE_ADDRESS` gets a page from the Caddyfile's catch-all `https://` block saying what to set; without it Caddy answers an empty 200, a blank white page. Caddy omits the port from its http→https redirect when `https_port` matches, so non-443 setups need the port in the address.
- `install.sh`: one-command install or update for Linux servers (systemd, glibc), run as root with `bash -c "$(curl … main/install.sh)"`; macOS and Linux without systemd use `install-docker.sh`. The repo is public and stays so: both installers download the source from `github.com/<repo>/archive/<branch or tag>.tar.gz`, with no token handling, and install the newest `vX.Y.Z` tag (`latest_release`, from GitHub's tags API; it greps every name out of the reply and uses `sort -V`, since the reply can arrive on one line, which once made it pick the last name, v1.0.0) unless `CRAFTY_BRANCH` is set. Without `CRAFTY_BRANCH` or `CRAFTY_TARBALL`, `install.sh` refuses a version older than the one in `app/` (`app_version`). One script, two parts: as root (`root_main`) it installs curl/tar if missing, creates the `crafty` account (`CRAFTY_USER`), adds it to `systemd-journal`, then hands its own text (`this_script`: `BASH_EXECUTION_STRING`, or the file) to that account via `runuser … env -i … CRAFTY_PHASE=user`; afterwards it writes the two services, checks the ports are free and starts them. As the account (`user_main`) it does everything under `~crafty/crafty-accounting`: downloads the app into `app.new`, re-runs itself from `app.new/install.sh` when that one has `user_main` (`CRAFTY_REEXEC`, since `crafty update` starts the outgoing version's copy), its own Node 22 from nodejs.org, a pinned Caddy (`CADDY_VERSION`, checked against its SHA-512 list) in `caddy/`, `npm ci --ignore-scripts` (better-sqlite3's bundled prebuilds instead of compiling) and the build, `.env`, the `crafty` script (replaced by moving a new file in, since the old one may still be running), then swaps `app.new` for `app` keeping `app.old` until the new one answers (`roll_back` otherwise). Run by the account itself (`crafty update`, Settings → Updates) it also restarts the services; it refuses if they aren't installed yet. Services (`SERVICES_VERSION`; bump it when they change, and an update without root then says to rerun as root): `crafty-accounting` runs `crafty app` (node, `HOST=127.0.0.1`, so only Caddy reaches it) with `KillMode=process`, so an update the app started survives the app being stopped; `crafty-caddy` runs `crafty caddy` with only `CAP_NET_BIND_SERVICE` (ambient), for ports 80/443. Both `Restart=always`: the account can't use systemctl, so `crafty restart` as the account kills each service's main process and waits for systemd to start it again (Caddy first, then the app: a page that started an update reloads once the new app answers, and came up blank when Caddy was still restarting; it also checks the new page's files load first, `reloadWhenReady`), with `kill -9` after 10 seconds, and just waits for a service that systemd is already starting again after a crash (as root it uses `systemctl restart`). The Caddyfile's `grace_period 5s` matters here: by default Caddy waits forever on stopping for open connections, and every open page holds one (`/api/events`), which made updates from v1.8.0 time out and roll back. Logs go to the journal (`crafty log`). It always serves HTTPS with the repo's `Caddyfile` (shared with Docker; the differences come in through `CADDY_HTTP_PORT`, `CRAFTY_UPSTREAM`, `CRAFTY_OTHER_ADDRESSES` and friends), certificates in `caddy/data` (`XDG_DATA_HOME`). Off port 443, `crafty caddy` appends the port to each `SITE_ADDRESS` entry and leaves `https_port` at 443: Caddy only puts the port in its http→https redirect when the address's port differs from `https_port`. Installs from v1.8 and earlier (run as a normal user with `crafty start`, pid files, maybe a `@reboot` crontab line, maybe ports 8080/8443) are moved over by `stop_unmanaged` and `write_settings` when root runs the installer.
- `uninstall.sh`: removes the `install.sh` install completely, as root, after listing it and asking for `delete` (`CRAFTY_CONFIRM=yes` skips that): the services, the account with its home (only if the home holds nothing else but skeleton dotfiles, else just the folder), its crontab and processes, `DATA_DIR` if `.env` moved it outside (only when `safe_to_remove`), the `crafty-accounting-auto-*.zip` files in a moved `BACKUP_DIR`, and installer copies left in `/tmp`. It refuses a Docker install. Keep it in step when the installer starts leaving something new behind.

## Rules

- **Database changes go in a new migration.** Append a new version to `MIGRATIONS` in `server/src/db/migrations.ts`; don't edit one that has shipped. Until real books are in use, editing migration 1 is possible but ask first, since dev databases and backups use it. Restore runs migrations on older backups, so a new migration must also upgrade an old dump; add a test for that.
- **Money** is integer pence everywhere; convert only for display, CSV and the MTD payload. Dates are ISO `YYYY-MM-DD`. Tax years are stored as `2025-26` and shown as `2025/26`.
- **Exports:** each CSV export (`export.csv`) has a JSON twin (`export.json`, same query, sent by `sendJsonExport` in `server/src/jsonExport.ts`) that keeps the structure, such as an expense's line items. JSON money is integer pence in fields ending `Pence`, except the MTD quarter, which is HMRC's own payload in pounds. The client offers both through `ExportMenu`. The income and expense JSON exports can be imported again (`POST /api/{incomes,expenses}/import`, after `…/import/preview`; `server/src/transactionImport.ts`, `ImportButton`): each row goes into the tax year its date falls in, its category is found by name, else by `hmrcCode` among the standard ones, and rows the books already have (same date, description or payee, amount and payment method, counting repeats) are left out. All or nothing: any problem and nothing is imported. Ignored: ids, `createdBy`/`updatedBy` (the importer is recorded), the computed totals (an expense's `totalPence` must still match its lines) and documents (only names are in an export). Keep the import in step when an export's fields change.
- **Expense totals:** `expenses.total_pence` is always the sum of the line items, worked out by the server; the API doesn't take a total.
- **Categories** carry an `hmrc_code` (MTD field name). Custom categories (`is_custom`) roll up to the standard category they map to.
- **Profit figures** use allowable expenses only (disallowable excluded): dashboard boxes, monthly chart, and the Reports → Breakdown Profit box. Category tables still list disallowable amounts, marked. Entertainment and depreciation are never allowable: their lines are always saved as disallowable (`isNeverAllowable`), and depreciation isn't offered for new lines or custom categories (cash basis), though HMRC's field stays and goes as zero.
- **First sign-in:** with no one set up, the first person is `ADMIN_NAME` (default `Admin`) with `ADMIN_PASSWORD`, or the default password `admin` (`DEFAULT_ADMIN_PASSWORD`) and `users.must_change_password` set. While it's set, `passwordChangeGuard` refuses every API call but changing their own password (and `/api/auth`), and the client shows `ChooseNewPassword` instead of the app. There's no `.env.example`: every setting has a default, the installers write `.env`, and the README's Configuration table lists them.
- **People** (Settings → Users; "users" in the UI): each has their own sign-in (shown as Username; `name` in the database, API and `ADMIN_NAME`) and active tax year (`users.active_tax_year_id`), and a role: `editor` or `viewer` (read-only). `readOnlyGuard` in `routes/auth.ts` refuses every change from a viewer (except switching their tax year and changing their own password) and backup downloads; the client hides editing with `useCanEdit()` and `EditorOnly`. New routes that change data are covered automatically; new editor-only downloads need adding to `EDITOR_ONLY_DOWNLOADS`. People belong to the install, not the books: they're left out of backups and kept through a restore or reset, so transactions store `created_by`/`updated_by` as names, not user ids.
- **Working together:** every successful non-GET API call is broadcast to the other open browsers over `GET /api/events` (Server-Sent Events), which refetch. Edit forms fill once and send `expectedUpdatedAt`; the server answers 409 if the record changed since, and the form offers to load the other version.
- **Documents** live in the `documents` table (one transaction can have up to `MAX_DOCUMENTS`), stored in `uploads/` under their original filenames, which must be unique. Uploads go through `saveWithDocuments` in `documents.ts`, which places the files, runs the database write and cleans up either way. The old `document_filename` columns on incomes and expenses are unused (always NULL since migration 6). **Take photo** (`useCameraOption` in `CameraDialog.tsx`): touch devices use `<input capture>`, which also works over plain HTTP; other devices use `getUserMedia` in `CameraDialog`, which browsers only offer on HTTPS or localhost, so on plain HTTP the dialog explains that instead. Photos, and files picked with iPhone's default name `image.jpg`, get a generated name (`photoFilename`) and go through `compressPhoto` in the browser: a JPEG of at most `MAX_PHOTO_BYTES`, with what it can't read (HEIC outside Safari) left as it is. Other chosen files are never changed. Files can also be dragged onto `DocumentField`, which treats them as if chosen; while it's on the page, a file dropped elsewhere is refused rather than opening in the tab and losing the form. New documents can be renamed in `DocumentField` before saving, keeping their extension; Save waits while a name is invalid or clashes on that transaction, and a clash elsewhere comes back as the server's 409.
- **Mileage** is stored in tenths of a mile and claimed at HMRC's rates for the tax year (`MILEAGE_RATES`, by the year they start from), worked out in date order per tax year (the 10,000-mile car threshold). Claims count as `carVanTravelExpenses` in every total.
- **Use of home** is hours per tax month (`home_working_months`), claimed at HMRC's flat rate as `premisesRunningCosts`, each month's claim dated its last day (the 5th). Mileage and use of home claims reach every total through `yearEntries`, `mileageClaimLines` and `useOfHomeClaimLines` in `repo.ts`; use those rather than querying expense lines directly.
- **Compare years** (`GET /api/reports/year-comparison`, `shared/src/yearComparison.ts`): `period=same` stops both years at the same day and month, the last date recorded in the later year (`comparisonCutoff`), and leaves out tax; `period=full` includes it. The page defaults to `same` while the later year is running. Columns follow the order chosen, but changes always run from the earlier year to the later. An amount opens Breakdown's `DrillDown` window over the page, kept in the URL (`show`, `showYear`).
- **Tax rates** are per tax year in `TAX_RATES` (`shared/src/taxEstimate.ts`); add each new year when HMRC confirms it. Later years fall back to the latest rates with a warning.
- **SA103S forms** are per tax year in `SA103S_FORMS` (`shared/src/selfAssessment.ts`): box numbers, wording and the short-form turnover limit. When HMRC publishes each new form, compare it and add the year, reusing the same form if the boxes the app fills in haven't changed. Other years use the nearest form with a warning. Box figures aren't stored, so a new form needs no migration; if HMRC splits or merges boxes in a way categories can't follow, that needs a new category.
- **Trading allowance** is by the tax year it starts from in `TRADING_ALLOWANCES`, separate from the form because it changes before that year's form appears. Rates announced but not yet law or published carry a `provisional` note (as do `MILEAGE_RATES`); remove it once confirmed.
- **Updates** (`server/src/updates.ts`, `GET /api/updates`, Settings → Updates, the bell's `update` notification): releases are the `vX.Y.Z` tags, and both installers install the newest one unless `CRAFTY_BRANCH` says otherwise, so `APP_VERSION` matches the code running. The server checks GitHub's tags a minute after starting and every 12 hours (`UPDATE_CHECK=false` stops that, not Check now), keeping the result in memory, and lists the commits since the running version's tag. How it applies one depends on the install (`config.updates.install`): `native` (the Linux quick install, detected by running from `<dir>/app` next to `crafty` and `node/`) saves a backup and runs `crafty update` with `CRAFTY_BRANCH` set, detached and with only a few environment variables (`NODE_ENV=production` would make `npm ci` skip the build tools), logging to `logs/update.log`; the update stops this server and systemd starts the new one, and a browser that started it reloads once the server reports another version (`useUpdates`, kept running in `Layout` for that alone). If the updater exits while this server still runs, it failed and the old version keeps running. `docker` (`CRAFTY_INSTALL` in `docker-compose.yml`, the folder from `CRAFTY_DIR` in `.env`) shows the `install-docker.sh` command; `manual` explains the steps. Tests replace `ctx.updates.runUpdater`.
- **Notifications** (`server/src/notifications.ts`, `/api/notifications`, `NotificationBell` left of `UserMenu`): conditions the server notices, keyed by condition (`notifications.key`), so `raiseNotification` makes one once while it lasts (later calls only update the wording, quietly) and `resolveNotifications` deletes it when it ends; raised again later, it's new and unread. Read state is per person (`notification_reads`); the bell lists only unread ones, and viewers may mark theirs read (`READ_ONLY_ALLOWED`). `audience` is `all` or `editors`; both current kinds are editors only. Install-level like people: in `INSTALL_TABLES` and copied across a restore (`KEPT_TABLES`). Changes publish the `notifications` live-update area, which refetches only the bell. Kinds: `update` (`syncUpdateNotification` after each successful check: one for the newest release, removed once installed or replaced; at start-up it only clears versions already installed) and `low-space` (`checkDiskSpace` every 5 minutes for the data disk, and the backup disk if separate, using `lowSpaceThreshold` from `shared/src/diskSpace.ts` as Settings → Backup and Restore does; cleared at 1.25× the limit). A new kind needs an icon and tone in `NotificationBell`.
- **Submission method:** each tax year goes to HMRC by Self Assessment return or MTD (`tax_years.submission_method`); the sidebar shows only that year's section. MTD can't be chosen for a year before `MTD_FIRST_SEND_YEAR`. Quarterly updates can only be recorded or sent for MTD years, and an MTD year with any, recorded or sent (`mtdUpdateCounts`), can't go back to Self Assessment.
- **MTD:** no copy and paste of figures (digital links). Exports are files. Each year sends expenses by category or as one total (`tax_years.mtd_expenses`), for turnover below the VAT registration threshold: `consolidatedExpenses`, allowable only (HMRC's "sum of all allowable expenses"). HMRC refuses it alongside any other expense field (`RULE_BOTH_EXPENSES_SUPPLIED`); its spec doesn't say either way about disallowable amounts, which are left out because the total is already without them. So the payload and CSV change shape with the choice. Once a year's turnover reaches it, everything goes by category for the whole year (`mtdExpensesToSend`), whatever the setting: HMRC doesn't state a mid-year rule, but categories are always acceptable.
- **HMRC connection** (`hmrc_connections`, one row per `HMRC_ENV`): NINO and OAuth tokens. Install-level like people: left out of backups (`INSTALL_TABLES` in `backup.ts`) and kept through a restore or reset. Call HMRC's APIs with `callHmrc(ctx, req, …)`: it adds the token (`hmrcAccessToken` refreshes once for concurrent callers) and the fraud prevention headers, and turns HMRC's errors into HttpErrors (never 401, which would sign the person out). Routes that call HMRC live under `/api/hmrc/`, so the client sends the browser's part of the fraud prevention data (`X-Fraud-Prevention`, from `client/src/lib/fraudPrevention.ts`). Never invent a header value HMRC can't be given truthfully; leave it out. Quarterly updates go through `POST /api/hmrc/quarters/:taxYearId/:quarter/send` with the payload the person confirmed (`mtdPayload`); the server rebuilds it and refuses (409) if it differs. A sent record (`mtd_submissions.sent_*`) is never changed by hand. The final declaration (`POST /api/hmrc/final-declaration/:taxYearId`, recorded in `mtd_final_declarations` per HMRC service) agrees to an `intent-to-finalise` calculation; the server reads it again and refuses (409) if it has errors or its total differs from the one shown, and a declared year takes no more quarterly updates except Q4, the whole year, as part of an amendment. Amendments (`/amendment/calculation`, then `/amendment`; `intent-to-amend`, `confirm-amendment`, recorded in `mtd_amendments`) are allowed until `mtdAmendmentDeadline`, 12 months after the filing deadline. Develop against the sandbox; `HMRC_ENV` defaults to it.
- **Submitted figures stay editable, on purpose:** no locking, because MTD updates are cumulative and amendments start with correcting the books. Instead `SubmittedFiguresNotice` warns on any change to figures HMRC has (a sent or recorded quarter, a final declaration, a filed return) and says how to put it right, and the Quarterly updates and Year-end summary pages say when the figures differ from those saved: `mtd_submissions.sent_payload` or `recorded_payload` (only the latest quarter matters, as a later update covers earlier ones) and `tax_years.sa_filed_figures`. On a record made by hand, a new date means filed again and saves the figures afresh; the same date keeps them. Records from before migration 17 have no saved figures, so they only get the warning.
- **Connection hidden without credentials:** HMRC won't approve new software for now, so everything about connecting to HMRC stays out of sight unless `HMRC_CLIENT_ID` and `HMRC_CLIENT_SECRET` are set (`HmrcStatus.configured`). Without them `GET /api/hmrc` reports no connection, NINO or business (the saved row is kept for when they return), the rest of `/api/hmrc` is 404, and the client hides Settings → HMRC and the Final declaration tab (still shown, without amending, for a year already declared). Records of what was sent stay visible. MTD years then use the CSV export and recording by hand. New HMRC features follow the same rule. README.md and the installers don't mention the connection; its setup is in `docs/connecting-to-hmrc.md`, which the README doesn't link to.
- **Claude integration** (Settings → Claude Integration, `/api/claude`, `server/src/claudeSettings.ts`, `shared/src/claude.ts`): an Anthropic API key and a model (`CLAUDE_MODELS`), in `claude_settings`. Install-level like the HMRC connection: in `INSTALL_TABLES` and `KEPT_TABLES`, so out of backups and kept through a restore or reset. A new key is checked with Anthropic first (`ctx.claude.checkKey`, `models.retrieve` on the chosen model) and never sent back in full: `GET` gives `keyHint` (`claudeKeyHint`). Editors change it; viewers see the hint. Not in `.env`.
- **Reading invoices** (`server/src/invoiceReader.ts`, used by scanning below; Add expense no longer reads one itself): with a key saved, a PDF or photo goes to Claude (structured output against the expense categories, depreciation left out) and comes back as an `InvoiceReading` that fills the form (the prompt asks for ledger-style line descriptions of about 60 characters, shortening long product titles; Claude also answers `amazonOrder`, and Amazon orders always get the payee `Amazon` (`AMAZON_PAYEE`), whichever seller the invoice names, and the payment method card; likewise `temuOrder` gives the payee `Whaleco UK Limited (Temu)` (`TEMU_PAYEE`) and card); nothing is saved until the person presses Save, and the file read is attached too, renamed by the pattern in Settings → Claude Integration → Document names (`claude_settings.filename_pattern`, NULL for the default `{date}_{payee}_{invoice}_£{amount}`; fields in `FILENAME_FIELDS`, rendered by `invoiceFilename` in `shared/src/invoiceFilename.ts`: a field not read is left out with the text before it, and it can still be renamed before saving). Only documents Claude read are renamed. Claude's reply is checked by `toInvoiceReading`, which drops what doesn't fit and adds warnings (unknown categories, lines not adding up to the total, no date or payment method). Images over 5 MB and HEIC aren't sent (the browser compresses photos first). Anthropic errors become 4xx/5xx HttpErrors, never 401. Server-side refusal fallbacks are sent except for Haiku, which has none. Tests replace `ctx.claude`. `api-check-alt`/`web-check-alt` (ports 3103/5175) and `api-check-3`/`web-check-3` (3104/5176) are further check pairs for when other chats hold 3102/5174. The app allows five dev servers per folder; when that leaves no room for `web-check-3`, build the client (`npm run build -w client`) and `api-check-3` serves it from `client/dist` on its own (delete the build afterwards).
- **Scanning in bulk** (`server/src/scans.ts`, `/api/scans`, `ScanDocuments` at `/expenses/scans`, the Scan documents button on Expenses with a count of those to check): many invoices uploaded one per request into the `scans` table, files in `uploads/` as `scan-<hex>.<ext>` (not served by `/api/documents`; `GET /api/scans/:id/file`). `ScanReader` (`ctx.scans`) reads waiting ones with Claude two at a time in the background (`kick` after an upload, a retry, a key being saved, and on each list request; `resume` at start-up and after a restore puts any left `reading` back to `waiting`), and publishes the `scans` live-update area, which refetches only that list. A file Claude can't read (HEIC, a large image) is kept as `failed`, to fill in by hand. Checking one opens the expense form at `/expenses/new?scan=<id>` (remounted per scan), filled from the reading with the file attached as if chosen, in the tax year its date falls in. Its fill counts as loaded, not changed, so leaving only asks after edits. Saving sends `scanId`, and the server deletes the scan in the same write (409 if it's gone); Add and check next, Skip for now, Open document (the file in a window of its own, the same one each time) and Discard document sit in a card above the form, with only Claude's warnings under them (no bottom buttons, so moving on needs no scrolling), and move on with `nextScanToCheck`. Scans are books data: in backups (files and rows), emptied by a reset. Adding needs a key (404 without); the list doesn't. Editors only.
- **Disk space for documents:** `ensureSpaceFor` in `documents.ts` refuses (507) to store a document that would leave the data disk below `minimumFreeForUploads` (room for the next backup like the newest, at least 200 MB), for scans and transactions' documents alike (`saveWithDocuments`); changes without documents still save. `GET /api/scans` reports the room left so the page warns before uploading a pile that won't fit. Tests replace `ctx.diskSpace`.
- **UI conventions:**
  - Dark theme with indigo/violet accents; use the tokens in `index.css`, which also define the light print theme.
  - Red for destructive actions and expense amounts. Green (`ok`) for income. The dashboard's monthly chart is the exception: violet gradient bars for income, sky blue for expenses, labelled by the legend. Compare years' chart uses the same bars for its two years.
  - Delete and Remove buttons use the `softDanger` button variant (`SOFT_DANGER` in `ui.tsx`): red text on a light red background with a faint red border.
  - Payment badges: cash is amber, card is teal, bank transfer is indigo.
  - Sidebar icons are muted grey; only the current page's icon takes the accent colour.
  - Sub-pages use `SectionLayout`: `variant="tabs"` in Self Assessment (Year-end summary), Making Tax Digital (Quarterly updates), Simplified Expenses (Mileage, Use of Home) and Reports (Tax estimate, Breakdown, Compare years); a section with one page shows no tabs, the side menu in Settings. A section's own address opens the sub-page last shown in that browser tab (sessionStorage), if still shown, else the first; it has no index route, and passes `ready={false}` while which sub-pages show is loading.
  - The page header (`PageHeader`, with `SectionLayout`'s tabs passed in as `tabs`) is pinned to the top of the window on desktop; phones pin only their top bar.
  - Dialogs are centred `<dialog>` elements with a blurred backdrop.
  - Leaving a transaction form with unsaved changes asks first (`useLeaveGuard` in `FormShell.tsx`): Cancel, Back, the sidebar and the browser's back button through react-router's `useBlocker` (so the app uses a data router, `createBrowserRouter`, with the routes still in `App`), closing or reloading the tab through `beforeunload`. Saving leaves with its `leave`, which doesn't ask. Escape leaves as Cancel does; it listens on window and skips a handled key, so a popup listening on document that closes on Escape must call `preventDefault`.
  - Table sorting (`useSort` in `transactions.tsx`) is remembered per table in that browser (localStorage, `crafty.sort.<table>`); a saved column that no longer exists falls back to the default.
  - Income and Expenses put their buttons in the table card's header, after the title and a divider, icon only: the filter toggle (`FilterToggle`; the search and filters start hidden, and showing them is remembered per table for that browser tab, `useFiltersShown`, sessionStorage; a red dot while hidden filters are in use), then Add, Import, Export and, for editors, Delete shown (`DeleteShownButton`, `softDanger`: deletes every row the filters match, across all pages, by id through `POST /api/{incomes,expenses}/delete`, after a warning where they type `delete`). With nothing shown, Export (`count` 0) and Delete shown stay in place, greyed out. The count says "filtered" while a filter is in use. Their detail views do the same in the card's top row: the amount, a divider, then icon-only Edit, Duplicate and Delete (`softDanger`), with the payment badge on the right.
  - Long tables (Income, Expenses, Mileage trips) are split into pages with `usePagination` and `Pagination` (`components/Pagination.tsx`): the page is in the URL (`?page=`), the page size remembered in localStorage: one choice for the transaction tables (`crafty.pageSize`), while Breakdown's Spending by payee keeps its own (`sizeKey`, `crafty.pageSize.payees`).
