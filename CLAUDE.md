# Crafty Accounting

Self-hosted bookkeeping for UK sole traders (cash basis), filing by Self Assessment return or through HMRC's Making Tax Digital (MTD) self-employment APIs. It started out for craft fair sellers (the sample data still is), but isn't limited to them. Keep README.md user-facing and short; implementation detail belongs here. README.md covers features, setup, Docker, HTTPS and backups; read it first.

**Status:** v1.0.0 is released but not yet in use with real books (as of 2026-10-28), so changes to the app and database structure are still fine. It stays a self-hosted web app; a native macOS version was considered and dropped.

## Layout

npm workspaces, all TypeScript:
- `shared/` (`@crafty/shared`): consumed as source, no build. Tax years, money, categories, zod schemas, API types, MTD and SA103S calculations (`mtd.ts`, `selfAssessment.ts`), mileage rates (`mileage.ts`), use of home flat rate (`useOfHome.ts`), Income Tax and Class 4 rates and the tax estimate (`taxEstimate.ts`).
- `server/`: Express 5 + better-sqlite3, bundled with tsup. Routes in `src/routes/`, SQL in `src/repo.ts`, migrations in `src/db/migrations.ts`, backup/restore/reset in `src/backup.ts`, daily backups in `src/autoBackup.ts`, people and password hashing in `src/users.ts`, the live-update event stream in `src/liveUpdates.ts`, the HMRC OAuth connection, token refresh and `callHmrc` in `src/hmrc.ts` (calls go through `ctx.fetch`, which tests replace), HMRC's fraud prevention headers in `src/fraudPrevention.ts`. Tests in `src/app.test.ts` (Vitest + supertest against a temporary database).
- `client/`: Vite, React 19, react-router 7, TanStack Query, react-hook-form, Tailwind v4, Recharts, lucide-react. API hooks in `src/lib/queries.ts`, theme tokens in `src/index.css`.

## Commands

Node 22 comes from Homebrew and isn't on the default PATH. Prefix shell commands with:

```bash
export PATH="/opt/homebrew/opt/node@22/bin:$PATH"
```

- If `node_modules` is missing (it can be cleared between sessions), run `npm ci` first.
- `npm run typecheck`: shared, server and client.
- `npx vitest run`: all tests. Run both before every commit.
- `npm run build`, `npm run seed`, `docker compose up -d --build`.
- `install-docker.sh`: the Docker Compose equivalent (source and `.env` in `~/crafty-accounting`; it refuses a folder holding an `install.sh` install, and that one refuses a Docker folder; `COMPOSE_PROJECT_NAME=crafty-accounting` pinned in `.env`, so it shares volumes with a checkout run by hand; `CRAFTY_PROJECT` overrides it for tests). Its body is in `main()` so an update can overwrite the running file; run from an install's folder it updates that install. Browsers send no server name (SNI) for an IP address and Docker's port mapping hides the address they used, so Caddy's `default_sni` is set to `SITE_IP` (the installer writes it, and adds it on update from the IP in `SITE_ADDRESS`); without it, browsing by IP fails the TLS handshake. Any address not in `SITE_ADDRESS` gets a page from the Caddyfile's catch-all `https://` block saying what to set; without it Caddy answers an empty 200, a blank white page. Caddy omits the port from its http→https redirect when `https_port` matches, so non-443 setups need the port in the address.
- `install.sh`: one-command install or update for Linux servers (systemd, glibc), run as root with `bash -c "$(curl … main/install.sh)"`; macOS and Linux without systemd use `install-docker.sh`. The repo is public and stays so: both installers download the source from `github.com/<repo>/archive/<branch or tag>.tar.gz`, with no token handling, and install the newest `vX.Y.Z` tag (`latest_release`, from GitHub's tags API; it greps every name out of the reply and uses `sort -V`, since the reply can arrive on one line, which once made it pick the last name, v1.0.0) unless `CRAFTY_BRANCH` is set. Without `CRAFTY_BRANCH` or `CRAFTY_TARBALL`, `install.sh` refuses a version older than the one in `app/` (`app_version`). One script, two parts: as root (`root_main`) it installs curl/tar if missing, creates the `crafty` account (`CRAFTY_USER`), adds it to `systemd-journal`, then hands its own text (`this_script`: `BASH_EXECUTION_STRING`, or the file) to that account via `runuser … env -i … CRAFTY_PHASE=user`; afterwards it writes the two services, checks the ports are free and starts them. As the account (`user_main`) it does everything under `~crafty/crafty-accounting`: downloads the app into `app.new`, re-runs itself from `app.new/install.sh` when that one has `user_main` (`CRAFTY_REEXEC`, since `crafty update` starts the outgoing version's copy), its own Node 22 from nodejs.org, a pinned Caddy (`CADDY_VERSION`, checked against its SHA-512 list) in `caddy/`, `npm ci --ignore-scripts` (better-sqlite3's bundled prebuilds instead of compiling) and the build, `.env`, the `crafty` script (replaced by moving a new file in, since the old one may still be running), then swaps `app.new` for `app` keeping `app.old` until the new one answers (`roll_back` otherwise). Run by the account itself (`crafty update`, Settings → Updates) it also restarts the services; it refuses if they aren't installed yet. Services (`SERVICES_VERSION`; bump it when they change, and an update without root then says to rerun as root): `crafty-accounting` runs `crafty app` (node, `HOST=127.0.0.1`, so only Caddy reaches it) with `KillMode=process`, so an update the app started survives the app being stopped; `crafty-caddy` runs `crafty caddy` with only `CAP_NET_BIND_SERVICE` (ambient), for ports 80/443. Both `Restart=always`: the account can't use systemctl, so `crafty restart` as the account kills each service's main process and waits for systemd to start it again, with `kill -9` after 10 seconds, and just waits for a service that systemd is already starting again after a crash (as root it uses `systemctl restart`). The Caddyfile's `grace_period 5s` matters here: by default Caddy waits forever on stopping for open connections, and every open page holds one (`/api/events`), which made updates from v1.8.0 time out and roll back. Logs go to the journal (`crafty log`). It always serves HTTPS with the repo's `Caddyfile` (shared with Docker; the differences come in through `CADDY_HTTP_PORT`, `CRAFTY_UPSTREAM`, `CRAFTY_OTHER_ADDRESSES` and friends), certificates in `caddy/data` (`XDG_DATA_HOME`). Off port 443, `crafty caddy` appends the port to each `SITE_ADDRESS` entry and leaves `https_port` at 443: Caddy only puts the port in its http→https redirect when the address's port differs from `https_port`. Installs from v1.8 and earlier (run as a normal user with `crafty start`, pid files, maybe a `@reboot` crontab line, maybe ports 8080/8443) are moved over by `stop_unmanaged` and `write_settings` when root runs the installer.

## Rules

- **Database changes go in a new migration.** Append a new version to `MIGRATIONS` in `server/src/db/migrations.ts`; don't edit one that has shipped. Until real books are in use, editing migration 1 is possible but ask first, since dev databases and backups use it. Restore runs migrations on older backups, so a new migration must also upgrade an old dump; add a test for that.
- **Money** is integer pence everywhere; convert only for display, CSV and the MTD payload. Dates are ISO `YYYY-MM-DD`. Tax years are stored as `2025-26` and shown as `2025/26`.
- **Exports:** each CSV export (`export.csv`) has a JSON twin (`export.json`, same query, sent by `sendJsonExport` in `server/src/jsonExport.ts`) that keeps the structure, such as an expense's line items. JSON money is integer pence in fields ending `Pence`, except the MTD quarter, which is HMRC's own payload in pounds. The client offers both through `ExportMenu`.
- **Expense totals:** `expenses.total_pence` is always the sum of the line items, worked out by the server; the API doesn't take a total.
- **Categories** carry an `hmrc_code` (MTD field name). Custom categories (`is_custom`) roll up to the standard category they map to.
- **Profit figures** use allowable expenses only (disallowable excluded): dashboard boxes, monthly chart, and the Reports → Breakdown Profit box. Category tables still list disallowable amounts, marked. Entertainment and depreciation are never allowable: their lines are always saved as disallowable (`isNeverAllowable`), and depreciation isn't offered for new lines or custom categories (cash basis), though HMRC's field stays and goes as zero.
- **First sign-in:** with no one set up, the first person is `ADMIN_NAME` (default `Admin`) with `ADMIN_PASSWORD`, or the default password `admin` (`DEFAULT_ADMIN_PASSWORD`) and `users.must_change_password` set. While it's set, `passwordChangeGuard` refuses every API call but changing their own password (and `/api/auth`), and the client shows `ChooseNewPassword` instead of the app. There's no `.env.example`: every setting has a default, the installers write `.env`, and the README's Configuration table lists them.
- **People:** each has their own sign-in (shown as Username; `name` in the database, API and `ADMIN_NAME`) and active tax year (`users.active_tax_year_id`), and a role: `editor` or `viewer` (read-only). `readOnlyGuard` in `routes/auth.ts` refuses every change from a viewer (except switching their tax year and changing their own password) and backup downloads; the client hides editing with `useCanEdit()` and `EditorOnly`. New routes that change data are covered automatically; new editor-only downloads need adding to `EDITOR_ONLY_DOWNLOADS`. People belong to the install, not the books: they're left out of backups and kept through a restore or reset, so transactions store `created_by`/`updated_by` as names, not user ids.
- **Working together:** every successful non-GET API call is broadcast to the other open browsers over `GET /api/events` (Server-Sent Events), which refetch. Edit forms fill once and send `expectedUpdatedAt`; the server answers 409 if the record changed since, and the form offers to load the other version.
- **Documents** live in the `documents` table (one transaction can have up to `MAX_DOCUMENTS`), stored in `uploads/` under their original filenames, which must be unique. Uploads go through `saveWithDocuments` in `documents.ts`, which places the files, runs the database write and cleans up either way. The old `document_filename` columns on incomes and expenses are unused (always NULL since migration 6). **Take photo** (`useCameraOption` in `CameraDialog.tsx`): touch devices use `<input capture>`, which also works over plain HTTP; other devices use `getUserMedia` in `CameraDialog`, which browsers only offer on HTTPS or localhost, so on plain HTTP the dialog explains that instead. Photos, and files picked with iPhone's default name `image.jpg`, get a generated name (`photoFilename`) and go through `compressPhoto` in the browser: a JPEG of at most `MAX_PHOTO_BYTES`, with what it can't read (HEIC outside Safari) left as it is. Other chosen files are never changed. Files can also be dragged onto `DocumentField`, which treats them as if chosen; while it's on the page, a file dropped elsewhere is refused rather than opening in the tab and losing the form. New documents can be renamed in `DocumentField` before saving, keeping their extension; Save waits while a name is invalid or clashes on that transaction, and a clash elsewhere comes back as the server's 409.
- **Mileage** is stored in tenths of a mile and claimed at HMRC's rates for the tax year (`MILEAGE_RATES`, by the year they start from), worked out in date order per tax year (the 10,000-mile car threshold). Claims count as `carVanTravelExpenses` in every total.
- **Use of home** is hours per tax month (`home_working_months`), claimed at HMRC's flat rate as `premisesRunningCosts`, each month's claim dated its last day (the 5th). Mileage and use of home claims reach every total through `yearEntries`, `mileageClaimLines` and `useOfHomeClaimLines` in `repo.ts`; use those rather than querying expense lines directly.
- **Compare years** (`GET /api/reports/year-comparison`, `shared/src/yearComparison.ts`): `period=same` stops both years at the same day and month, the last date recorded in the later year (`comparisonCutoff`), and leaves out tax; `period=full` includes it. The page defaults to `same` while the later year is running. Columns follow the order chosen, but changes always run from the earlier year to the later. An amount opens Breakdown's `DrillDown` window over the page, kept in the URL (`show`, `showYear`).
- **Tax rates** are per tax year in `TAX_RATES` (`shared/src/taxEstimate.ts`); add each new year when HMRC confirms it. Later years fall back to the latest rates with a warning.
- **SA103S forms** are per tax year in `SA103S_FORMS` (`shared/src/selfAssessment.ts`): box numbers, wording and the short-form turnover limit. When HMRC publishes each new form, compare it and add the year, reusing the same form if the boxes the app fills in haven't changed. Other years use the nearest form with a warning. Box figures aren't stored, so a new form needs no migration; if HMRC splits or merges boxes in a way categories can't follow, that needs a new category.
- **Trading allowance** is by the tax year it starts from in `TRADING_ALLOWANCES`, separate from the form because it changes before that year's form appears. Rates announced but not yet law or published carry a `provisional` note (as do `MILEAGE_RATES`); remove it once confirmed.
- **Updates** (`server/src/updates.ts`, `GET /api/updates`, Settings → Updates, the sidebar's notice under the version): releases are the `vX.Y.Z` tags, and both installers install the newest one unless `CRAFTY_BRANCH` says otherwise, so `APP_VERSION` matches the code running. The server checks GitHub's tags a minute after starting and every 12 hours (`UPDATE_CHECK=false` stops that, not Check now), keeping the result in memory, and lists the commits since the running version's tag. How it applies one depends on the install (`config.updates.install`): `native` (the Linux quick install, detected by running from `<dir>/app` next to `crafty` and `node/`) saves a backup and runs `crafty update` with `CRAFTY_BRANCH` set, detached and with only a few environment variables (`NODE_ENV=production` would make `npm ci` skip the build tools), logging to `logs/update.log`; the update stops this server and systemd starts the new one, and a browser that started it reloads once the server reports another version. If the updater exits while this server still runs, it failed and the old version keeps running. `docker` (`CRAFTY_INSTALL` in `docker-compose.yml`, the folder from `CRAFTY_DIR` in `.env`) shows the `install-docker.sh` command; `manual` explains the steps. Tests replace `ctx.updates.runUpdater`.
- **Submission method:** each tax year goes to HMRC by Self Assessment return or MTD (`tax_years.submission_method`); the sidebar shows only that year's section. MTD can't be chosen for a year before `MTD_FIRST_SEND_YEAR`. Quarterly updates can only be recorded or sent for MTD years, and an MTD year with any, recorded or sent (`mtdUpdateCounts`), can't go back to Self Assessment.
- **MTD:** no copy and paste of figures (digital links). Exports are files. Each year sends expenses by category or as one total (`tax_years.mtd_expenses`), for turnover below the VAT registration threshold: `consolidatedExpenses`, allowable only (HMRC's "sum of all allowable expenses"). HMRC refuses it alongside any other expense field (`RULE_BOTH_EXPENSES_SUPPLIED`); its spec doesn't say either way about disallowable amounts, which are left out because the total is already without them. So the payload and CSV change shape with the choice. Once a year's turnover reaches it, everything goes by category for the whole year (`mtdExpensesToSend`), whatever the setting: HMRC doesn't state a mid-year rule, but categories are always acceptable.
- **HMRC connection** (`hmrc_connections`, one row per `HMRC_ENV`): NINO and OAuth tokens. Install-level like people: left out of backups (`INSTALL_TABLES` in `backup.ts`) and kept through a restore or reset. Call HMRC's APIs with `callHmrc(ctx, req, …)`: it adds the token (`hmrcAccessToken` refreshes once for concurrent callers) and the fraud prevention headers, and turns HMRC's errors into HttpErrors (never 401, which would sign the person out). Routes that call HMRC live under `/api/hmrc/`, so the client sends the browser's part of the fraud prevention data (`X-Fraud-Prevention`, from `client/src/lib/fraudPrevention.ts`). Never invent a header value HMRC can't be given truthfully; leave it out. Quarterly updates go through `POST /api/hmrc/quarters/:taxYearId/:quarter/send` with the payload the person confirmed (`mtdPayload`); the server rebuilds it and refuses (409) if it differs. A sent record (`mtd_submissions.sent_*`) is never changed by hand. The final declaration (`POST /api/hmrc/final-declaration/:taxYearId`, recorded in `mtd_final_declarations` per HMRC service) agrees to an `intent-to-finalise` calculation; the server reads it again and refuses (409) if it has errors or its total differs from the one shown, and a declared year takes no more quarterly updates except Q4, the whole year, as part of an amendment. Amendments (`/amendment/calculation`, then `/amendment`; `intent-to-amend`, `confirm-amendment`, recorded in `mtd_amendments`) are allowed until `mtdAmendmentDeadline`, 12 months after the filing deadline. Develop against the sandbox; `HMRC_ENV` defaults to it.
- **Submitted figures stay editable, on purpose:** no locking, because MTD updates are cumulative and amendments start with correcting the books. Instead `SubmittedFiguresNotice` warns on any change to figures HMRC has (a sent or recorded quarter, a final declaration, a filed return) and says how to put it right, and the Quarterly updates and Year-end summary pages say when the figures differ from those saved: `mtd_submissions.sent_payload` or `recorded_payload` (only the latest quarter matters, as a later update covers earlier ones) and `tax_years.sa_filed_figures`. On a record made by hand, a new date means filed again and saves the figures afresh; the same date keeps them. Records from before migration 17 have no saved figures, so they only get the warning.
- **Connection hidden without credentials:** HMRC won't approve new software for now, so everything about connecting to HMRC stays out of sight unless `HMRC_CLIENT_ID` and `HMRC_CLIENT_SECRET` are set (`HmrcStatus.configured`). Without them `GET /api/hmrc` reports no connection, NINO or business (the saved row is kept for when they return), the rest of `/api/hmrc` is 404, and the client hides Settings → HMRC and the Final declaration tab (still shown, without amending, for a year already declared). Records of what was sent stay visible. MTD years then use the CSV export and recording by hand. New HMRC features follow the same rule. README.md and the installers don't mention the connection; its setup is in `docs/connecting-to-hmrc.md`, which the README doesn't link to.
- **UI conventions:**
  - Dark theme with indigo/violet accents; use the tokens in `index.css`, which also define the light print theme.
  - Red for destructive actions and expense amounts. Green (`ok`) for income. The dashboard's monthly chart is the exception: violet gradient bars for income, sky blue for expenses, labelled by the legend. Compare years' chart uses the same bars for its two years.
  - Delete and Remove buttons use the `softDanger` button variant (`SOFT_DANGER` in `ui.tsx`): red text on a light red background with a faint red border.
  - Payment badges: cash is amber, card is teal, bank transfer is indigo.
  - Sidebar icons are muted grey; only the current page's icon takes the accent colour.
  - Sub-pages use `SectionLayout`: `variant="tabs"` in Self Assessment (Year-end summary), Making Tax Digital (Quarterly updates), Simplified Expenses (Mileage, Use of Home) and Reports (Tax estimate, Breakdown, Compare years); a section with one page shows no tabs, the side menu in Settings. A section's own address opens the sub-page last shown in that browser tab (sessionStorage), if still shown, else the first; it has no index route, and passes `ready={false}` while which sub-pages show is loading.
  - The page header (`PageHeader`, with `SectionLayout`'s tabs passed in as `tabs`) is pinned to the top of the window on desktop; phones pin only their top bar.
  - Dialogs are centred `<dialog>` elements with a blurred backdrop.
  - Escape leaves the transaction forms (`EscapeToCancel`), asking first if there are unsaved changes. It listens on window and skips a handled key, so a popup listening on document that closes on Escape must call `preventDefault`.
  - Date fields use `DateInput` (`components/DateInput.tsx`), not `<input type="date">`: dd/mm/yyyy text plus a calendar in the top layer, weeks starting Monday. `value` is still an ISO date. In react-hook-form it goes through `Controller`.

## Working in this repo

- Never read `.env`; it holds the owner's real password.
- The owner's own dev preview runs on ports 3101 (API) and 5173 (web); don't stop or restart it. For browser checks, start a separate copy (`api-check` and `web-check` in `.claude/launch.json` do this, signing in as `Admin` / `check-password`):
  - API on 3102, with `DATA_DIR` set to a scratch folder and a throwaway `ADMIN_PASSWORD`/`SESSION_SECRET`.
  - Vite on 5174, with `API_URL=http://localhost:3102`.
  - Load sample data with `POST /api/sample-data`.
  - `api-check` has no HMRC credentials, so the connection is hidden; `api-check-hmrc` is the same with made-up ones, to see it.
- Check UI changes in the browser.
- Commit and push each finished change to `main` (remote `koder-guy/crafty-accounting`).
- Bump `APP_VERSION` in `shared/src/index.ts` and the package versions for a release, then tag it.
